## Contracts and integration requests (no shared paths edited)

1. **XP normalization:** this code follows the *proposed contracts-v1* paragraph: balance retains pre-loss accumulated progress, positive debt records the deficit, gains pay debt first. It requires retained balance at least the earned-level threshold. Architecture's alternative phrasing (balance itself below threshold) must not be loaded into this convention: that would count the same loss twice. Integrator should replace the ambiguous `FLHCharacterRecord.ExperienceBalance/ExperienceDebt` comments in `Core/LHSaveSnapshot.h` with these exact semantics after review and freeze the conversion used by death/load. Do not silently migrate existing saves. Death loss denominator stays unresolved.
2. **Ruleset adapter/data:** consume the plain typed structs in `LHRules.h`. Integrator should either expose equivalent reflected fields on `ULHRulesetDefinition` or author a validated one-to-one adapter from its `Parameters/Policies/ExperienceThresholds` into these structs. Reject missing/duplicate/unrecognized keys; retain provenance. Creation outcomes need ordered answers, named attributes, unspent pool, resolution/provenance and an approved generation policy. These are not generic expression strings. No adapter or shared schema change is made here.
3. **Growth RNG serialization:** returned `Awards` and `AcceptedRolls` are index-aligned. Each roll has health/mana values and a caller-provided stable award ID. `FLHGrowthAward.RollInputs` remains empty until the integrator defines canonical `FLHRngState` algorithm/revision/byte encoding. The character owner must encode both accepted rolls into `RollInputs` before saving; exact consumed rolls are returned, not discarded. No native byte serialization convention is invented here. Validate award IDs against existing persisted history and request replay IDs in the authority layer; this function checks duplicates within one operation only.
4. **Build exposure:** if cross-module includes cannot find `Rules/LHRules.h`, add `PublicIncludePaths.Add(ModuleDirectory);` in integrator-owned `Lighthaven.Build.cs`, or move/export the approved module include surface through an integrator change. Existing test module already declares Lighthaven/Core/CoreUObject/Engine dependencies; no additional module/plugin is requested. Verify include visibility with real UBT before claiming it works.
5. **Policies:** Base/Effective selection, flat armor, resistance treatment, finite creation table and floor/quantum algorithms require integrator review and a labelled ruleset revision. No formula family is declared Confirmed. Replace algorithm/model as research resolves it rather than labelling synthetic constants authentic. Enum policy provenance is separate from numeric data. Existing arbitrary `FLHEligibility.Policies` are rejected rather than ignored; adapter must consume known policy vocabulary before calculation.
6. **Authority:** W2-02 resolves canonical records to inputs, reconstructs modifiers from uniquely equipped owned items, supplies approved growth attribute basis, validates accepted creation preview, commits only accepted outputs once and persists growth/carry. W1-03 validates target/life/resources/LOS/range and deduplicates activation/impact callbacks. Requirement success does not charge mana or teach a spell. Bow compatibility is caller-validated and does not assert that an inventory-only quiver is equipped.

`LIGHTHAVEN_API` exports ordinary structs' free functions; no new reflected/generated headers, actor/world access or module boilerplate is introduced. Runtime numeric inputs use double for fractional calculations and int64 for conservation/progression; integer addition detects overflow. Arithmetic is deterministic for a fixed build/platform; cross-architecture floating-point bit parity is not established.
