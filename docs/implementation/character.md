## Behavior and API

`ULHCharacterAuthorityComponent::Attach(PlayerState)` attaches one authority component to an authoritative PlayerState, returning its existing instance on repeat calls. It owns the native `FLHCharacterAuthority`; the avatar owns no durable record. The component is explicitly attached by the integrator because the PlayerState constructor is outside this task's scope. Ordinary level travel still requires export/import through the save/session owner; PlayerState lifetime is not a persistence guarantee.

Initialize once with a complete registered `FLHCharacterProfile`, bootstrap request epoch and an explicitly supplied seed. The profile holds typed Rules parameters, content/rules identity, creation policy/revision, initial resources/pools/gold, inventory slot capacity, item definitions and an explicit starter-item list. Mechanical defaults are Unresolved. No production startup HP, mana, gold, weapon, skill, spell, XP curve, growth formula, capacity or creation distribution is invented here. An explicitly supplied empty starter list means no free items. Starter items, when declared, receive stable run/origin/instance identities and resolved quantity one; they are placed in inventory without automatic equipping. They must pass the same complete item/capacity validation as acquired items.

The three frozen Execute overloads implement CreateCharacter, AllocateAttributePoints and EquipItem/unequip. The coordinator's owner-bound `ILHCommandHandler` routes these overloads to this component; unrelated service/combat/travel commands belong to their owners. Successful commands retain request epoch, digest and sequence; exact replay returns the original accepted sequence without mutation. Reused IDs with changed payload reject. At 4,096 receipts or exhausted sequence, new commands reject rather than dropping history. Creation assigns one CharacterId and campaign RunId; initial-save retries use the same committed record and receipt. Filesystem slot reservation and durable initial-save publication belong to W2-01, not this component.

`Preview(ordered four answers)` calls Rules.RollCreation on the declared finite outcomes, then authority-selects uniformly among the eligible table entries using the pinned FRandomStream. This is an explicit **prototype finite-table generator**, not recovered classic rolling or a distribution inferred from Bible examples. The supplied profile must declare and version that policy. Missing classic generation data blocks classic mode. The service retains one opaque PreviewToken, exact accepted creation record, unspent pool and post-roll state. Re-roll supersedes the earlier token. Commit compares the entire Creation struct, including provenance and seed evidence, to the issued preview. Forged attributes, invalid answers, stale tokens and second confirmations reject. Preview tokens are transient and absent from the save record; accepted creation inputs/revision/answers/attributes and generator evidence persist.

Names must be nonempty, at most 64 TCHAR code units, have no leading/trailing whitespace and contain no C0/DEL controls. This is an authored local UI policy, not a T4C historical restriction; it permits duplicate local display names. Appearance validates the frozen body/face/hair/skin/outfit catalog, expands the body's bundled face, rejects duplicates/unknown or incompatible selections and persists explicit sorted IDs. Appearance grants no mechanical benefits or kit.

Allocation requires five explicitly resolved nonnegative deltas and positive total, checks pool and integer overflow, and validates the candidate before committing. Accepted creation attributes are never replaced by later base attributes. Equipment bindings refer to owned stable inventory instances, have unique first-class slots including Quiver, and derive totals anew from base attributes, earned historical maxima and complete registered modifiers. No accumulated GAS/equipment totals are saved. A swap validates the entire resulting loadout atomically. Bow requirements call Rules.CheckRequirements with compatibility from the definition's explicit allowed-quiver list and an actually equipped Quiver binding; backpack-only quivers fail. Removing a required quiver rejects while its bow remains equipped. The service performs no per-shot quiver decrement. Unequipping resource-maximum gear clamps current resources down, and never heals on equip. Allocation/equipment while dead reject; already accepted replay is still returned.

Inventory items remain in the canonical inventory while equipped; equipment is a binding, so unequip consumes no extra inventory cell. Capacity checks both explicitly configured inventory-instance count and total quantity × registered weight against Rules-derived capacity. Items do not silently merge or overflow stacks. AddItem checks the full identity/definition/quantity, registered stack limit and weight; RemoveItem checks positive available quantity and rejects equipped instances. PermanentRolledValues are deliberately rejected until their key/unit adapter is registered; ignoring unknown rolled modifiers would be unsafe. These are trusted authority transaction primitives, not public loot commands. Gold-only pickup remains the loot owner's D11 transaction and has no inventory-capacity cost.

`GrantExperience` calls Rules.Advance once for all new thresholds, supplies one authority-minted ID and two RNG fractions per new level, appends every award and persists D07 roll pairs before committing. Growth basis must be explicitly Base or Effective. `AddExperienceDebt` adds nonnegative debt without reducing retained balance or earned level. Subsequent XP pays debt before increasing balance; recovering debt neither appends growth nor re-awards points. XP/debt/items operations are trusted settlement primitives; the reward/loot owner must deduplicate its source and settle both owners in a single world transaction before publishing or saving. They do not implement encounter reward claims by themselves.

## Frozen snapshot and integration seams

Export copies Character plus character identity, rules reference, transaction sequence, campaign identity, request epoch/receipts and creation/growth RNG into an existing FLHSaveSnapshot. It preserves the caller's unrelated world/session/header fields. Import validates before replacing state; it clears transient preview tokens and restores seeds. It checks registered inventory/equipment, resources/capacity, request epoch/digest/sequence/uniqueness, creation outcome against retained pre-roll seed, growth transition continuity and deterministic IDs, each growth award through Rules.Advance using its historical attributes/roll pair, historical maximum sums, and permanent attribute-point conservation. Skills/spells must have unique nonempty keys and skill ranks must be resolved/nonnegative. Full registry validation, cross-world ownership uniqueness, entrance/checkpoint legality, envelope integrity and completed-action boundaries remain W2-01/W2-04 responsibilities. Import is for a snapshot already validated by those owners, not a replacement file decoder.

D07 encoding uses `UE.FRandomStream`, revision 1, four little-endian current-seed bytes for RNG.Creation/RNG.Growth. Each award retains `LH.NormalizedRollPair`, revision 1, 16 bytes of little-endian binary64 Health then Mana under RNG.Growth. Import does not reroll historical awards or infer old growth from current attributes. Unknown/missing required states reject. Tests compare progression continuation before/after restoring saved state; native runtime execution is still required.

Two required function hooks keep shared serialization/reward contracts under their owners:

- `RequestDigest(command type, UScriptStruct, payload)` must return D04 lowercase 64-hex SHA256 over canonical `LHRequest1` bytes containing every field. Failure to return a 64-character digest rejects. The caller must implement the exact codec; character code does not claim reflection ExportText is that codec.
- `GrowthId(run, character ID, ToLevel)` must implement D06's SHA256 `LHReward1`/LevelGrowth source mapping and collision checks. Character checks nonzero IDs, history collisions and deterministic identity on import.

The tests inject deliberately **test-only** reflection/SHA1 fingerprints padded to 64 characters and deterministic GUID fixtures. Neither fixture is compiled into runtime character source or an approved published profile. Initialize rejects missing hooks. No Core change/version bump is requested.
